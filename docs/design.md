# 食品安全标签解读小程序 — 设计文档

- 日期：2026-08-27
- 状态：设计已确认，待进入实现计划
- 范围：第一版（V1）

## 1. 背景与目标

家用食品标签解读工具，微信小程序形态。核心场景：家人在超市货架前拿不定主意买哪个，拍下包装即可得到「能不能买、对谁不合适」的快速判断，并且每条结论都能追溯到依据。

### 定位约束

- **仅供家人使用，不推广、不上架。** 通过微信小程序**体验版**分发（未认证个人主体，开发者 + 体验成员合计上限 15 人）。体验版不走审核、不需要服务类目、不需要工信部备案。
- 该定位解除了个人主体的类目限制（「信息资讯」类目对个人主体未开放，「食品」类目需《食品经营许可证》），使完整功能得以实现。
- 该定位一旦改变（对外推广），本文档的合规前提全部失效，见 §9。

### 场景优先级

用户确认的两个场景：

- **A（V1 实现）**：超市货架前快速判断。要求三秒出结果，容忍不完整。
- **C（V2 规划）**：核验老人购买的保健品资质真伪。价值更高但触发频率低，且依赖外部数据源。

V1 只做 A。C 的实现路径已探明（见 §8），接口预留。

### 输出形态

默认给通用红绿灯结论；配置了家庭成员体质后，切换为按成员的个性化判断（例：「⚠️ 爸爸不建议：钠超标；✅ 孩子可以」）。

个性化是本工具相对于市面通用添加剂查询工具的唯一差异点，且它把「解读」从开放式论述题变成了有明确判据的判定题，实现难度反而更低。

## 2. 关键技术决策

### 2.1 架构：微信云开发

采用小程序云开发（云函数 + 云数据库 + 云存储），不自建后端。

理由：

- **绕开域名备案。** 小程序请求自建后端需已 ICP 备案的 HTTPS 域名；云函数调用不受此约束。
- **API Key 有安全存放位置。** 视觉模型的 key 不能放在小程序前端（可被反编译），云函数是服务端环境。
- 无需购买服务器与证书；自带数据库与存储；免费额度对 5 人用量绰绰有余。

自建后端会额外引入域名备案、服务器运维、HTTPS 证书三项负担，对家用工具不划算。

### 2.2 标签提取：多模态大模型直接输出结构化 JSON

将包装照片直接交给视觉模型，返回结构化 JSON（配料、营养成分、执行标准、SC 号等）。

**放弃的方案：** 传统 OCR（腾讯云/百度）+ 自研解析器。配料表在曲面瓶身上变形、反光、分栏，字号极小，OCR 输出顺序常错乱；营养成分表需依赖坐标重建行列。解析器会退化为大量脆弱的分支逻辑，每种新版面都需打补丁。

多模态模型在内部完成版面理解、乱序纠正、表格重建，对倾斜与反光的容忍度显著更高。成本约每张几分钱，家庭用量每月数元。

**核心收益不只是省事：** 它把项目中最不可控的部分（版面解析）从「需要编写并长期维护的代码」转为「模型能力」，工作量从约两周压缩到约两天，且遇到异形包装无需改码。

### 2.2.1 模型选型约束

微信云函数运行在境内，访问境外 API 存在延迟与稳定性风险，而本工具要求「三秒出结果」。因此**优先选用境内可直连的国产多模态模型**（如豆包、通义千问、GLM 等视觉版本）。

`extractLabel` 内部对模型的调用需封装在单一适配层之后，使更换模型只影响一个文件；§11 的回归集正是为「更换模型后验证是否退化」而建。

### 2.3 两条配套约束（防止 2.2 翻车）

1. **模型只负责「抄」，不负责「判断」。**
   模型的唯一职责是把包装上印的字准确转为 JSON。是否超标、对谁不友好，全部由确定性规则判定。这保证结论可复现、可解释、可追溯，不会今天说能吃、明天说不能吃。这正是「证据化」得以成立的前提。

2. **「识别结果确认」步骤强制，不可跳过。**
   模型会看错小字号数字。扫描后先展示识别到的关键数值，用户可核对、可手动修改，之后才出结论。一秒钟的交互成本，换掉「把 120 看成 1200 导致十倍误差、进而给出错误饮食建议」的风险。考虑到输出会真实影响家人的饮食决定，此步骤不可省略。

### 2.4 扫码的定位

`wx.scanCode` 扫条码本身免费可用，但国内没有可靠的免费「条码→商品」数据库。V1 主路径为**拍照**；条码仅用于给历史记录做标识、以及判断产地（69 开头为中国大陆）。

## 3. 架构与数据流

```
小程序端                    云函数                      云数据库
─────────                  ─────────                   ─────────
拍照/扫码
   ↓ 上传云存储
 fileID  ──────────────→  extractLabel
                          （调 VLM，只抄不判断）
                                ↓ 标签 JSON
识别结果确认页 ←────────────────┘
   ↓ 用户核对/修正
修正后的标签 ─────────────→  normalize
                          （单位归一到 /100g）
                                ↓
                    ┌───────────┴───────────┐
                    ↓                       ↓
                 evaluate            verifySC（校验码，纯算法）
        ←── members（家庭成员）              ↓
        ←── rules（阈值表）           decodeSC ←── regions / categories
                    ↓                       ↓
                    └───────────┬───────────┘
                                ↓ 判定结果 + SC 核验结果
证据化报告页 ←──────────────────┘
   ↓
                                              ──→   scans（历史快照）
```

## 3.1 命名约定（实现阶段确立）

**所有标识符一律 ASCII，中文只出现在给人看的字符串值里。**

起因是 WXML 的表达式解析器不接受非 ASCII 标识符：`{{识别备注.length}}` 报
`unexpected 识 at pos0`，`data-字段="x"` 报 `unexpected character`。
而云函数返回的字段要一路传到 WXML 渲染，因此这条约束会穿透整个数据链路——
不只是前端，云函数的返回结构、模型输出的 JSON 键名都必须是 ASCII。

曾考虑在云函数出口加一层中英映射以保住内部的中文命名，否决了：
两套命名容易漂移，而且为了保住一个本就不该有的决定去加复杂度是不划算的。

具体做法：
- 字段名、变量名、函数名、事件处理器名：ASCII
- `summary`、`evidence`、`message`、`verdict` 等**字段的值**：中文，因为要给家人看
- 营养素等内部 key（`sodium`、`transFat`）在展示前经 `NUTRIENT_LABEL` 映射成中文名，
  测试里有断言禁止内部 key 泄漏到面向用户的文案中

## 4. 组件划分

边界按「能否独立测试」切分：

| 组件 | 唯一职责 | 依赖 | 可测性 |
|---|---|---|---|
| `extractLabel` | 图片 → 标签 JSON，**只抄不判断** | VLM API | 需真实图片，建小样本回归集 |
| `normalize` | 单位归一化（/份、/100ml → /100g） | 无 | 纯函数，单元测试 |
| `evaluate` | 标签 + 成员画像 → 判定结果 | 无网络、无 IO | 纯函数，单元测试，**核心** |
| `verifySC` | SC 号校验码验证（第一层） | 无 | 纯函数，单元测试 |
| `decodeSC` | SC 号查表解码（第二层） | 区划表、类别表（作为参数传入） | 用假表单测 |

**划分要点：** 只有 `extractLabel` 是不确定的（模型输出会变），其余全为确定性纯函数。项目中约 90% 的逻辑可被完整单测覆盖，出问题时能一眼定位是「抄错了」还是「判错了」。

单位归一化（例：「每份 30g，含钠 360mg」→ 「1200mg/100g」）独立成 `normalize`，因为换算过程本身需要展示给用户，属于证据链的一环。

## 5. 规则引擎：「证据化」如何落地

判定规则存为数据，不写成条件分支（以下阈值为格式示例，实际取值在实现阶段依据来源确定）：

```json
{
  "指标": "钠",
  "阈值": 800,
  "单位": "mg/100g",
  "比较": ">",
  "适用人群": ["高血压"],
  "等级": "warn",
  "依据": "GB 28050 营养素参考值 NRV 钠 2000mg/日；《中国居民膳食指南(2022)》建议高血压人群每日钠摄入 <1500mg"
}
```

每条规则自带 `依据` 字段。报告中每条结论均可展开，显示「因为钠 1200mg/100g > 阈值 800mg/100g，依据为该规则 `依据` 字段所记载的标准出处」。

**证据化报告不是最后附加的导出功能，而是从规则的数据结构里长出来的。**

连带收益：调整阈值无需改码；新增关注点（如痛风盯嘌呤）只是加一条数据；结论永远可复现。

## 6. SC 码校验：分层设计与数据依赖

SC 号格式为 `SC` + 14 位数字：3 位食品类别编码 + 6 位行政区划代码（省2/市2/县2）+ 4 位企业顺序码 + 1 位校验码。

### 第一层：校验码算法（零数据依赖）

采用 GB/T 17710 规定的 MOD 11,10 算法，纯计算，永不过期。可确定性判定「该编号系编造」，能拦截随手编造的低级伪造。

### 第二层：查表解码（有数据依赖，会过期）

- 前 3 位 → 食品类别，查《食品生产许可分类目录》
- 4-9 位 → 行政区划，查民政部行政区划代码表

**更新周期不同：** 行政区划代码由民政部**每年更新**（撤县设区、区划调整每年都有）；分类目录**不定期修订**，间隔数年。

### 关键风险与应对

SC 证按**发证当时**的区划编码。一张 2018 年发的证使用 2018 年的区划码；若该县此后撤县设区、代码变更，用最新表查询将**查不到**。若此时按「查不到 = 非法」处理，会给完全合法的产品报红灯。

因此定为硬规则：

> **第二层查表仅用于「解码展示」，永远不产出「不合格」结论。查不到即为「未知」，不是「非法」。只有第一层校验码算法可以得出「该编号有问题」。**

报告呈现对应三种情况：

- 校验码不通过 → 「⚠️ 该编号校验位不符，可能有误或系伪造」
- 校验码通过 + 查表命中 → 「标称产自 XX 省 XX 市 XX 区，类别：糕点」，并与包装标注产地做一致性提示
- 校验码通过 + 查表未命中 → 「编号格式有效；产地代码 3210xx 未在现行区划表中，可能为历史区划，无法进一步核实」

### 数据存储与更新

两份表存**云数据库**（`regions`、`categories`），不打包进代码：更新数据无需重新部署；可保存多个年度版本以覆盖历史区划；每条数据带来源与抓取日期，报告中可标注「依据：民政部行政区划代码 2025 版」。

更新方式为**手动触发**的一次性脚本，一年运行一次。不做自动定时任务——为一年一次的更新维护定时任务与失败告警不划算，且来源页面改版会导致定时任务静默失败，反而比手动更新更不可靠。

V1 灌入**现行版本 + 往前三年**的区划表，覆盖绝大多数在售商品的证。

## 7. 数据隔离与鉴权

`members`（体质档案）与 `scans`（扫描历史）挂在 `familyId` 下，而非个人 openid 下——一家人共享同一份成员配置与历史记录。

### 两条铁律

1. **数据库集合权限设为「仅管理端可读写」，前端一律不直连数据库。**
   所有读写经由云函数。客户端权限规则在「家庭」这种比个人大、比全局小的粒度上容易配错导致越权；全走云函数使权限逻辑收敛到唯一位置，可审计。

2. **`familyId` 必须服务端反查，绝不接受前端传参。**
   云函数用 `cloud.getWXContext().OPENID` 获取调用者身份（微信侧注入，前端无法伪造），再反查该 openid 所属家庭，只查询该家庭的数据。

   若让前端传 `familyId`，任何人改一个参数即可读取他人数据。此类越权在正常使用中永远不会触发，因此常规测试无法发现，必须在设计阶段定死。

### V1 实现程度

数据模型带 `familyId`、云函数强制按 openid 反查——V1 即做对，成本接近于零。**邀请加入家庭的完整流程（邀请码、审批、退出）V1 不做**，手动写入家人 openid 即可。待真有第二个家庭使用时再补界面。

## 8. 错误处理

因输出会被家人当真，**静默失败是本项目最危险的失败模式**：若模型未识别出钠含量，`evaluate` 收到 `undefined` 若被当作 0 处理，报告会显示绿灯「可以吃」——这比直接报错严重得多。

三条硬规则：

1. **缺失即声明，绝不当作零。** `extractLabel` 对每个字段必须返回「是否在图上找到」，未找到即为 `null`，报告明写「未识别到钠含量，本项无法判断」。宁可少给结论，不能给错结论。
2. **模型输出必须过 schema 校验。** VLM 偶尔返回非法 JSON 或幻觉出图上没有的数值。校验失败重试一次，再失败转手动录入，不做猜测。
3. **确认页强制，不可跳过。**（见 §2.3）

其余失败（照片模糊、配料表未拍全、网络超时）统一走同一模式：明确告知失败环节与后续操作，不做无限等待。

**措辞约束：** 报告中不出现「不能吃」等绝对化表述，采用「不建议，建议咨询医生」。本工具是家庭参考工具，非医疗建议；正因家人会真的采信，措辞更需留有余地。

## 9. 非目标（V1 明确不做，且不留半成品）

- ❌ **执行标准核对** — 需 GB 标准全文库，标准文本存在版权问题，且「核对」逻辑的复杂度被严重低估
- ❌ **SC 许可联网核验** — 国家企业信用信息公示系统反爬极强，个人难以自动化
- ❌ **官方抽检查询** — 数据分散于总局与各省，PDF/HTML 混杂，无 API
- ❌ **保健食品批准文号核验（场景 C）** — V2 实现，接口预留。路径已探明：市场监管总局特殊食品信息查询平台公开可查，支持按产品名称、批准文号、备案号、申请人企业、社会信用代码查询国产与进口保健食品。核验批准文号（`国食健注G/J`、`国食健备G/J`，老产品为 `卫食健字`）与产品名、企业、获批保健功能是否一致，可精准命中老人被骗的典型骗局
- ❌ **条码查商品库** — 国内无可靠免费数据源
- ❌ **同类对比** — 需 `scans` 积累历史数据后才有价值

原始设想的六环节链路，V1 实际交付约两个半环节。但这部分是每周都会使用的，且**不依赖任何外部数据抓取——没有任何功能会因第三方网站改版而失效**，这对需要长期维护的家用工具至关重要。

## 10. 数据模型

| 集合 | 内容 | 备注 |
|---|---|---|
| `families` | familyId、创建者 openid、成员 openid 列表 | V1 手动维护 |
| `members` | 家庭成员及关注点（高血压 → 盯钠；血糖高 → 盯糖与代糖；儿童 → 盯添加剂与反式脂肪） | 挂 familyId |
| `scans` | 原图 fileID、标签 JSON、判定结果快照 | 挂 familyId |
| `rules` | 判定规则阈值表，含 `依据` 字段 | 全局共享 |
| `regions` | 行政区划代码表，多年度版本，带来源与抓取日期 | 全局共享 |
| `categories` | 食品生产许可分类目录，带来源与抓取日期 | 全局共享 |

**原图保留。** 家庭用量一年数百张，几乎不占空间；发现判断有误时，有原图才能回溯是「抄错了」还是「判错了」。

## 11. 测试策略

- `normalize` / `evaluate` / `verifySC` / `decodeSC` —— 纯函数，常规单元测试覆盖，这是主战场
- `extractLabel` —— 从家中橱柜选取 20 个真实包装拍照，人工标注正确答案，构建回归集。更换模型或修改 prompt 后跑一遍即可发现退化。这是唯一能防住「模型悄悄变笨」的手段
- `verifySC` 的 MOD 11,10 校验码算法用真实 SC 号验证，正例与反例均需覆盖
- **WXML 静态检查** —— WXML 不经过 Node，只在开发者工具里编译，前端这层本来没有任何
  自动化验证。`test/wxml.test.js` 把已踩过的坑固化成断言：属性名非 ASCII、表达式含非 ASCII
  标识符、表达式里调用 `indexOf`/`map` 这类方法（不报错但静默失效）、页面文件成对存在且已在
  `app.json` 注册
- 端到端流程手动验证

## 12. 合规边界（若定位改变）

以下前提**仅在「不推广、仅家人使用」时成立**，一旦对外提供服务全部失效：

- **体验版 15 人是硬上限**（未认证个人主体，开发者 + 体验成员合计）。这是能打开该小程序的微信号总数上限。
- 正式发布需过审核、需服务类目、需工信部备案。而「信息资讯」类目对个人主体未开放，本工具的功能形态大概率会被判入该类目。
- **家庭成员的健康状况（高血压、糖尿病）属于《个人信息保护法》定义的敏感个人信息**，处理需取得单独同意，并承担相应告知与安全保障义务。自家使用不涉及，对外提供服务则是实打实的合规义务。

**结论：隔离设计 V1 即做对（成本为零），但不为「推广」做任何额外投入。** 真需要推广时，主要障碍是主体资质与合规（注册个体工商户、重新过类目），代码改动反而很小。当前的隔离设计只是为那一天保留可能性。
